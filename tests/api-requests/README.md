# Домашнє завдання: API + UI, зміна аватарки

## Як запустити

```bash
npm install
npx playwright test tests/api-requests
```

Потрібні змінні в `.env`: `BASE_URL`, `API_URL`, `ORIGIN`.
Акаунт для цього тесту готувати не треба: новий користувач створюється через API під час кожного запуску.

## Структура

- `app/controllers/UsersController.controller.ts` — API-контролер: створення, логін і редагування користувача
- `tests/api-requests/fixtures/fixtures.ts` — фікстури:
  - `token` — створює користувача через API і повертає його токен;
  - `login` — авторизує браузер цим токеном через `storageState`, без форми входу;
  - `request` — API-контекст із заголовком `Authorization: Token <jwt>`
- `tests/api-requests/fixtures/StorageHelper.ts` — формує `storageState` із токеном у `localStorage`
- `tests/api-requests/users.data.ts` — генерація тестових даних (faker)
- `tests/api-requests/register-api.spec.ts` — реєстрація через API
- `tests/api-requests/settings-avatar.spec.ts` — зміна аватарки через UI
- `tests/api-requests/avatar-img.gif` — файл аватарки для завантаження

## Дослідження авторизації: Dojo Articles

1. Реєстрація: `POST /api/users` → `201`. У відповіді об'єкт `user` з полем `token` (JWT).
2. Фронтенд зберігає токен у `localStorage` під ключем `qa-dojo.token`.
3. Кожен API-запит авторизованого користувача має заголовок `Authorization: Token <jwt>`.
4. Cookies для авторизації не використовуються.

## Дослідження авторизації: власний проєкт (знеособлено)

> Конкретні запити, адреси та опис проєкту не публікуються (умови NDA).
> Тут лише принцип роботи авторизації та як він впливає на автотести.

1. Неавторизованого режиму немає: без входу доступна лише сторінка логіну.
   Отже, кожен UI-тест потребує авторизованої сесії.
2. Після логіну дані авторизації зберігаються в сесії
   і автоматично передаються в усіх запитах до бекенду.
3. Висновки для автоматизації:
   - логін через UI виконується один раз (setup / globalSetup), стан зберігається у файл
     і перевикористовується тестами, щоб не логінитись у кожному тесті;
   - тестові дані для сценаріїв краще створювати через API з тією ж сесією, а не через UI;
   - сесія має обмежений строк дії, тому в setup її треба оновлювати перед прогоном;
   - файл зі станом сесії не комітиться (`.auth/` додано в `.gitignore`).
